# Student Registration & Mode Analysis

## Current System Overview

### Authentication Architecture
- **Backend**: NestJS with JWT-based authentication
- **Frontend**: React with Zustand state management
- **Auth Flow**: Login → JWT Access Token + Refresh Token → API requests

### Current User Structure
```
User Entity:
├── id (UUID)
├── firstName
├── lastName
├── email (unique)
├── password (hashed with bcrypt)
├── role (references Role entity)
├── location (JSON: province, district, sector, schoolId)
├── isActive (boolean)
├── phone
├── department
├── avatarUrl
├── lastLoginAt
└── refreshToken (hashed)
```

### Current Authentication Endpoints

#### Login (`POST /auth/login`)
- Requires: email, password
- Returns: user object + accessToken + refreshToken
- Validates user.isActive = true
- Updates lastLoginAt

#### Refresh (`POST /auth/refresh`)
- Requires: userId, refreshToken
- Returns: new accessToken + refreshToken
- Validates refresh token hash

#### Logout (`POST /auth/logout`)
- Clears refresh token
- Requires JWT guard

#### Get Profile (`GET /auth/me`)
- Returns current user data
- Requires JWT guard

### Current User Management Endpoints

#### Create User (`POST /users`)
- Requires: MANAGE_USERS permission
- Admin-only endpoint
- Bulk upload support via XLSX

#### List Users (`GET /users`)
- Requires: VIEW_USERS permission

#### Update Profile (`PATCH /users/me/profile`)
- Public endpoint (authenticated only)
- Can update: firstName, lastName, phone, department

#### Change Password (`PATCH /users/me/password`)
- Public endpoint (authenticated only)
- Validates current password

## Issues Identified

### 1. No Self-Registration (Student Signup)
- Currently, students cannot register themselves
- All users must be created by admins via bulk upload
- Lacks student-facing registration UI

### 2. No Student-Specific Role/Mode
- User roles are generic (super_admin, admin, gis_analyst, viewer)
- No dedicated "student" role with student-specific permissions
- No student-specific views or features

### 3. No Email Verification
- Users are created directly without email confirmation
- Passwords are generated by admins
- Lacks security for self-signup

### 4. Role-Based Access Control Limitations
- Permissions are static and array-based on Role
- No dynamic permission system
- Limited scope enforcement (hierarchical access)

## Database Migration Strategy

```sql
-- Add columns to users table
ALTER TABLE users ADD COLUMN IF NOT EXISTS email_verified BOOLEAN DEFAULT false;
ALTER TABLE users ADD COLUMN IF NOT EXISTS email_verification_token VARCHAR;
ALTER TABLE users ADD COLUMN IF NOT EXISTS email_verification_expiry TIMESTAMP;
ALTER TABLE users ADD COLUMN IF NOT EXISTS account_type VARCHAR DEFAULT 'student';
ALTER TABLE users ADD COLUMN IF NOT EXISTS registration_source VARCHAR DEFAULT 'admin';
ALTER TABLE users ADD COLUMN IF NOT EXISTS terms_accepted_at TIMESTAMP;

-- Create user_verifications table
CREATE TABLE IF NOT EXISTS user_verifications (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token VARCHAR UNIQUE NOT NULL,
  type VARCHAR NOT NULL,
  expires_at TIMESTAMP NOT NULL,
  is_used BOOLEAN DEFAULT false,
  created_at TIMESTAMP DEFAULT now(),
  updated_at TIMESTAMP DEFAULT now()
);

CREATE INDEX idx_user_verifications_token ON user_verifications(token);
CREATE INDEX idx_user_verifications_user_id ON user_verifications(user_id);
```

## Risk Mitigation

| Risk | Mitigation |
|------|-----------|
| Email service failure | Implement queue system (BullMQ) for retry |
| Token collision | Use cryptographically secure random tokens |
| Scope leakage | Enforce scope checks on every query |
| Rate limit bypass | Implement IP-based + email-based throttling |
| Email phishing | Add security headers, SPF/DKIM/DMARC |
